# Google Play Data Safety Form

**Reconciled 2026-10-02 against the actual release build** (`pubspec.lock`,
`lib/`, `android/`). This supersedes the earlier version of this document, which
predated the Firebase Cloud Messaging dependency.

> **Read this first.** The answers below describe what the shipped binary
> **does**, not what the code was written to do. Where those differ, the shipped
> behaviour wins, and the difference is called out.

---

## 0. The FCM finding (this is the whole reason the doc was rewritten)

`pubspec.yaml` declares `firebase_core ^3.10.0` and `firebase_messaging ^15.1.1`
(resolved to `firebase_core 3.15.2` / `firebase_messaging 15.2.10` in
`pubspec.lock`). The previous version of this document listed FCM device tokens
as collected-and-shared.

**In the build that actually ships, FCM does not run.** Verified:

| Requirement for FCM on Android | State in this repo |
|---|---|
| `android/app/google-services.json` | **absent** (file does not exist) |
| `com.google.gms.google-services` Gradle plugin applied | **no** — absent from `settings.gradle.kts` and `app/build.gradle.kts` |
| `lib/firebase_options.dart` | **hand-written placeholder**, not generated by `flutterfire configure` |
| Values inside that placeholder | `String.fromEnvironment('WEEKEND_FIREBASE_*')` → empty strings unless explicitly defined |

`notification_service.dart::_initFirebase()` calls
`Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform)`. With
empty `apiKey`/`appId`/`messagingSenderId` this throws, and the surrounding
`catch` logs `FCM not configured (using local notifications only)` and returns.
`_firebaseInitialized` stays `false`, so `_saveDeviceToken()` returns immediately
and **no row is ever written to `device_tokens`**.

### What this means for the form

**Declare NO device identifiers as collected, and NO sharing of device
identifiers, unless and until FCM is actually configured.**

Declaring an FCM token that is never generated is a false statement in a
Google-owned declaration. Play requires the form to match the binary.

### If FCM is switched on before launch

Only after all of the following are done does the Device-Identifiers row become
true, and it must then be re-declared:

1. A real Firebase project exists and `flutterfire configure` has regenerated
   `lib/firebase_options.dart` (or equivalent values are supplied).
2. `android/app/google-services.json` is committed (it contains no secret; it is
   a public config file — but confirm that before committing).
3. The `com.google.gms.google-services` plugin is applied.
4. A backend sender actually posts to FCM. **Note: none exists.** There is no
   Edge Function or scheduled job in `supabase/functions/` that sends push. Even
   a working client token would have nothing to deliver it.
5. The Data Safety form is updated to declare the token, its purpose
   (app functionality / push delivery) and its recipient (Google, as the FCM
   processor).

Until steps 1–5 are complete, leave it out.

## How to fill the form

Play Console → **Setup → App content → Data safety**. For each data type set
**Collected?**, **Shared?**, **Purpose** and **Destinations**.

### Location

| Form field | Collected | Shared | Purpose | Destination |
|---|---|---|---|---|
| Approximate location | **Yes** | No | App functionality (nearby discovery, distance) | — |

> The app requests `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION`, but
> `LocationService` uses a reduced accuracy for discovery. Exact coordinates are
> stored **only** on the user's own profile row and consumed server-side by
> PostGIS. `toApproximateCoordinates()` fuzzes coordinates before they leave the
> device, geohash precision 7 is used for crossed-paths, and only a rounded
> `distance_km` and a city/locality string reach other users. Verified in
> `lib/services/location_service.dart` and `lib/models/crossed_path.dart`.
### Photos and media

| Form field | Collected | Shared | Purpose | Destination |
|---|---|---|---|---|
| Photos | Yes | No | App functionality (profile) | — |
| Audio (voice data) | Yes | No | App functionality (voice intros) | — |

> Photos go to the **private** `profile-photos` bucket, scoped to the user's own
> folder. Each row carries `moderation_status`; only `approved` photos are
> visible to other users. `ImageOptimizer` re-encodes on upload, which **strips

> itself does not retain capture-time location, device or timestamp data.
>
> `RECORD_AUDIO` is declared for the optional voice-intro feature. Recording
> only ever starts on an explicit user action.

## Data shared with third parties

| Recipient | Data | Purpose | Notes |
|---|---|---|---|
| **Supabase** (backend hosting) | Email, profile data, photos, messages, location | App functionality | Postgres + PostGIS + Auth + Storage + Realtime + Edge Functions |
| **AI providers** (server-side only) | See below | App functionality | Called from Edge Functions only; keys are server-side |
| Google Play services | Install attribution, in-app updates | Platform requirement | Provided by the platform, not an SDK in the app |

### AI providers

Inference happens **only** inside Edge Functions. The client never calls a
provider directly and holds no provider credential.

| Data sent | Purpose | Where |
|---|---|---|
| Verification selfie + ID document | Photo verification | `photo-verification` Edge Function |
| Message text + context | Translation | `translate-message` Edge Function |
| Prompt answers + interests | Icebreaker generation | `serve-ad` / icebreaker Edge Function |

## Data not collected

To answer these Play questions **"No"**:

- Precise geolocation (only the approximate/fuzzed form above)
- Health and fitness
- Financial account information (purchase history only)
- Contacts
- Calendar
- SMS or call logs
- Installed apps
- Web browsing history
- Advertising ID / device identifiers
- Diagnostics (crashes, logs)

## Encryption in transit

All traffic is HTTPS. `android:usesCleartextTraffic="false"` is set in
`android/app/src/main/AndroidManifest.xml` and enforced further by
`res/xml/network_security_config.xml`.

## User rights and deletion

Users can:

- **Access** — export their data in-app.
- **Rectify** — edit the profile.
- **Restrict** — disable location discovery and distance display in Location
  settings.
- **Delete** — delete the account in-app. An `account-deletion` Edge Function and
  service-role RPCs exist to remove the auth user, profile rows and storage
  objects.

Play requires that account deletion be reachable **both** in-app and via a
web request. The in-app path exists in code but is **unverified on a device**,
and the external web-request mechanism is **not yet confirmed to be published**.
Both must be live before submission — see `docs/HUMAN_ACTIONS_REQUIRED.md` §5.

## Notes on sensitive data

- Weekend does **not** access the camera outside the photo-upload, verification
  and QR-scanner flows, and every one of those starts from an explicit user
  action.
- The photo pipeline strips EXIF metadata before upload.
- Exact coordinates are never returned to another user; only a rounded distance
  and a locality string are.
These are disclosures Play requires because user content reaches a third party.
The recipients are not named in the app; confirm the current provider
identities and their own data-processing terms server-side before submitting,
and disclose the correct company names in the form.

### Advertising

Weekend serves **contextual** ads from its own `serve-ad` Edge Function. There
is **no AdMob, Facebook Audience Network, Unity Ads or any other ad-network
SDK** in `pubspec.lock`. Ad selection does not use the user's profile or
location.
