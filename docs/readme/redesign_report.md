## 3. Screenshots: how they were produced

Every screen image is a **genuine render of the production widget tree**, not a
mock-up drawn by hand and not artwork. The harness in `tool/readme_capture/`:

1. Pumps the real screen widget — `DiscoverScreen`, `ExploreScreen`,
   `MatchesScreen`, `ChatScreen`, `ProfileScreen`, `PlansScreen`,
   `SafetyCenterScreen` — inside the app's own `WeekendAtmosphere` and
   `AppTheme.darkTheme`.
2. Replaces only the Riverpod state with synthetic fixtures. The screen code,
   the design system and the theme are untouched.
3. Renders at 412 × 915 logical pixels with a device pixel ratio of 3
   (1236 × 2745), which is a current Android handset.
4. Writes the result to `assets/readme/raw/` as a golden image.

```bash
flutter test tool/readme_capture/screens_capture_test.dart --update-goldens
flutter test tool/readme_capture/chat_capture_test.dart --update-goldens \
  --dart-define=SUPABASE_URL=http://127.0.0.1:54123 \
  --dart-define=SUPABASE_ANON_KEY=sb_fixture_readme_capture
python tool/readme_capture/build_readme_assets.py
```

### Provenance and honesty

- **All content in the images is synthetic.** Names, cities, bios, interests,
  timestamps and the chat transcript are invented fixtures
  (`tool/readme_capture/fixtures.dart`).
- **No photograph of a person appears anywhere.** The avatars are abstract
  brand-coloured monograms generated by `tool/readme_capture/make_fixtures.py`.
  There is no real likeness, no real conversation, no email address, no phone
  number and no location coordinate in the published set.
- **The screens are the shipped screens.** No screen was invented to fill a
  gap. Every image corresponds to a screen that exists in `lib/features/`.
- **The chat transcript is real app behaviour.** `ChatScreen` renders its
  transcript from a PostgREST stream, so the capture runs a small loopback
  server that answers the two reads the chat screen performs and speaks enough
  of the Supabase Realtime protocol to accept the channel join. The bubbles,
  the coral "sent" gradient, the Translate affordance and the timestamps are
  the production widget's own output.
- **The Weekend Plans image is labelled.** The Plans screen is complete and
  wired to the database, but its entry point is not routed in the shipped app.
  The README marks this with a footnote and repeats it under Known
  limitations, so the image is never read as "shipped and reachable".

### One deliberate deviation

`DiscoverScreen` calls `ref.listen` from `initState`. Riverpod and the Flutter
framework both guard that with assertions that only exist in debug builds; the
release binary runs the same code with the assertions stripped, which is why
the app works on device. The capture harness renders that screen through a
custom element that resolves the provider container without registering an
inherited-widget dependency, so the capture matches the release build. **No
application code was changed to achieve this** — see limitation 7.1 below.

### A GitHub rendering gotcha worth knowing

GitHub starts a new HTML block for every line that begins with a tag. The
technology badges were originally written one `<img>` per line, so GitHub
rendered them as a **vertical stack** even though the source looked like a
row. Putting the badges on a single line restores the horizontal run; the
rendered HTML now contains no `<br>` between them.

The fixed `width` attributes were dropped at the same time — they scaled each
shield to a different height and left the row with a ragged baseline. At their
natural size every badge is the same height and lines up. The rule is now
recorded in `docs/SEO.md` so it is not reintroduced.

## 7. Limitations and findings

### 7.1 `DiscoverScreen` calls `ref.listen` from `initState`

`lib/features/discovery/discover_screen.dart:41`. Riverpod asserts that
`ref.listen` is used inside `build`, and the Flutter framework separately
asserts that an inherited-widget dependency is not registered during
`initState`. Both assertions are debug-only, so **a debug build of Weekend
crashes on the Discover tab while the release build works**. The capture
harness works around it without touching application code, but the assertion
itself should be fixed — moving the `ref.listen` call into `build` is a
one-line change. This was left alone because the brief excludes changes to
Flutter business logic.

### 7.2 Weekend Plans is not reachable in the shipped app

`lib/features/plans/plans_screen.dart` is fully implemented and wired to the
`plans` and `plan_participants` tables, but `PlansScreen` is not in the router
and is not embedded in any tab. The README marks this rather than presenting
Plans as a shipped, reachable feature.

### 7.3 The release asset name does not follow the CI convention

The release workflow publishes `Weekend-v<version>-release.apk`, but the
current v2.8.5 release was uploaded as `app-release.apk` and carries no
`.sha256` file. The README and `docs/installation.md` link the real published
asset and describe checksum verification generically. Worth reconciling with
the workflow so every release has a predictable name and a checksum.

### 7.4 No beta channel, no Play Store listing, no Discussions

The repository has no closed or open beta, the app is not published to Google
Play, and GitHub Discussions are disabled. The brief asked for a "Join Beta
Testing" link; because no such channel exists, the hero links to the release
page as "Test builds" instead of pointing at something that does not exist. No
Play Store badge is shown for the same reason.

### 7.5 `SECURITY.md` still points at an old checksum example

`SECURITY.md` verifies `Weekend-v2.2.0-release.apk`, which is no longer the
current release. The security policy itself was not changed, per the brief;
this is a documentation follow-up.

### 7.6 Repository metadata: published, with one manual step left

The GitHub repository settings were updated through the REST API:

- **Description** — now
  *"An open-source Android dating and social discovery app. Discover nearby
  people, match, chat and make real-world plans."*
- **Topics** — 14 focused tags, down from 20 with duplicates:
  `android`, `dart`, `dating-app`, `flutter`, `kotlin`, `location-based`,
  `matchmaking`, `open-source`, `postgis`, `postgresql`, `privacy`,
  `real-time-chat`, `social-discovery`, `supabase`.
  Removed as redundant or filler: `dating` (duplicated `dating-app`),
  `open-source-app` (duplicated `open-source`), `mobile-app`,
  `social-network` (duplicated `social-discovery`), `weekend` (brand term, not
  a search term) and `ai-moderation`.

**The custom social preview image still has to be set by a maintainer.** GitHub
exposes no public API for it — `PATCH /repos/{owner}/{repo}` silently ignores a
`social_preview` field and there is no `PUT /social-preview` route. Set it in
the browser:

> Repository → Settings → General → Social preview → Upload
> `assets/readme/weekend-hero.png` (1280 × 640)

Until that is done, shared links use the repository's default preview rather
than the Weekend banner.

### 7.7 Passkeys remain disabled server-side

The client implementation is complete, but the live Supabase project answers
`passkey_disabled`. The README states this under Known limitations and does
not list passkeys as an operational feature.

### 7.8 The capture harness is tooling, not application code

`tool/readme_capture/` sits outside `test/`, so `flutter test` does not run it
and CI is unaffected. It does add three Dart files and three Python scripts to
the repository.

## 8. How to regenerate the assets

```bash
# 1. Synthetic avatars (monograms, never photographs)
python tool/readme_capture/make_fixtures.py

# 2. Real screen renders
flutter test tool/readme_capture/screens_capture_test.dart --update-goldens
flutter test tool/readme_capture/chat_capture_test.dart --update-goldens \
  --dart-define=SUPABASE_URL=http://127.0.0.1:54123 \
  --dart-define=SUPABASE_ANON_KEY=sb_fixture_readme_capture

# 3. Mockups and banners
python tool/readme_capture/build_readme_assets.py

# 4. Validate
python tool/readme_capture/validate_readme.py
python tool/seo_audit.py --online
```

The chat capture binds a fixed loopback port (54123) and the screen captures
use port 54124, because `flutter_cache_manager` reuses the file it stored for a
given URL. Change both together if the ports move.
